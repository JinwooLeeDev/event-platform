Busan Play 2-B 사전 준비 — 최소 검증 (2026-11-21)

현재 확인
- 브랜치 feat/다국어지원, 기존 미커밋 변경 보존.
- GEMINI_API_KEY / GEMINI_MODEL: 현재 프로세스 환경과 .env 모두 미등록.
- GEMINI_TRANSLATION_WORKER_ENABLED: 미등록, application.yml 기본값 false.
- SUPABASE_DB_URL / SUPABASE_DB_USERNAME / SUPABASE_DB_PASSWORD: .env 등록됨.
  값은 출력하지 않았다. IDE 실행 설정/원격 서버의 환경 변수는 별도 확인 대상이다.
- build -x test 성공. 테스트 실행 없음. 실제 DB 연결/변경 및 Gemini 호출 없음.
- 기존 1-A~2-A 코드, EventService/Controller/DTO/Mustache/업무 로직은 수정하지 않았다.

로컬 설정 준비
.env 또는 실제 실행 프로세스 환경에 GEMINI_API_KEY와 GEMINI_MODEL을 직접 등록한다.
키를 채팅이나 Git에 올리지 않는다. worker-enabled는 false로 유지한다.
모델은 해당 Google 프로젝트에서 사용 가능한 무료 모델을 명시한다. 자동 모델 대체는 없다.

Supabase SQL 적용 방법 — 실행 전 사용자 승인 필요
1. 접속 정보에 해당하는 Supabase 프로젝트의 SQL Editor를 연다.
2. 다음 읽기 쿼리로 대상 테이블 존재 여부를 확인한다.

select to_regclass('public.events') as source_table,
       to_regclass('public.event_translation') as cache_table,
       to_regclass('public.translation_job') as job_table,
       to_regclass('public.translation_budget') as budget_table;

3. public.events가 존재하고 신규 3개 테이블이 모두 없을 때만 적용한다.
   하나라도 이미 있으면 이 절차로 변경하지 않고 기존 스키마부터 확인한다.
4. build/i18n2b-prep/apply-new-tables.sql 내용을 SQL Editor에서 실행한다.
   원본 db/manual/event-translation.sql에 BEGIN/COMMIT, public search_path,
   기존 신규 테이블이 발견되면 중단하는 보호 조건만 감싼 파일이다.
   새 테이블 3개, 인덱스 2개와 새 budget 테이블의 초기 행 1개만 만든다.
   기존 테이블/행 변경이나 초기화는 없다. 오류 시 ROLLBACK한다.

승인 후 실제 테스트 절차 — 영어 1건, 최대 실제 API 호출 1회
1. 기존 Spring Boot 앱을 새로 시작하지 않고 별도 일회성 검증 실행기로 접속한다.
   Hibernate DDL과 demo-data.sql 시드를 실행하지 않는다. 자동 worker는 활성화하지 않는다.
2. 아래 읽기 쿼리로 기존 PUBLISHED 행사 후보 1개를 선택한다.
   없으면 자동 생성/상태 변경하지 않고 사용자에게 보고한다.

select id, length(title) as title_length, length(summary) as summary_length,
       length(description) as description_length
from public.events
where status = 'PUBLISHED'
order by id
fetch first 1 rows only;

3. 선택한 행사 본문이 외부 전송 가능한 공개 소개인지 확인한다.
   title/summary/description만 전송하며, 주소/개인정보 필드는 전송하지 않는다.
4. 캐시와 기존 대기/진행 작업을 읽어 확인한다. 다른 작업이 있거나 자동 worker가
   실행 중이면 중단한다. 기존 캐시/작업을 삭제하거나 변경해 테스트를 강행하지 않는다.
5. 선택한 eventId, locale=en으로 EventTranslationService.requestTranslation을 호출한다.
   캐시가 없으면 기존 TranslationWorker.runOne을 딱 한 번 수동 실행한다.
   테스트 설정 maxRetries=0, requestsPerDay=1로 추가 호출을 방지한다.
   캐시가 이미 있으면 재사용만 확인하며 실제 연결 확인을 위해 임의로 삭제하지 않는다.
6. COMPLETED와 event_translation의 동일 event_id/locale/source_hash 저장을 확인한다.
7. 같은 requestTranslation/findTranslation을 다시 호출해 같은 번역과 캐시 반환을 확인한다.
   worker를 다시 실행하지 않고 job/예산 사용량이 증가하지 않는지 읽어서 확인한다.
8. 행사 원본 세 필드와 status가 실행 전후 동일한지 비교한다. 로그에는 키/원문을 출력하지 않는다.
   성공/실패 코드와 저장/캐시 여부만 보고한 후 중단한다.
